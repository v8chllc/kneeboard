Kneeboard tracker wireframe

Static reference drawing for the tracker display model. No JavaScript, no build step, not carried into application code. Rows are transcribed from the sanitized fixtures in tests/fixtures/simbrief; identifiers, coordinates, and distances are fixture values. Coordinates and RDIS are derived by hand using the rules in docs/tracker-behavior.md.

Home flight simulation only. Not for real-world navigation.

Display questions this drawing exists to settle

  • State encoding uses a glyph, a word, and weight, so nothing depends on color alone. Are six states distinguishable at a glance, or should skipped and ineligible rows read more differently?
  • The rail is one continuous left bracket with end caps, drawn per row so it survives page divisions. Is a bracket the right metaphor, or should members be marked individually?
  • Queued fixes show slot numbers in outline badges and pending or entered slots show filled badges. Does the outline badge read as informative or as noise this far ahead of the aircraft?
  • Page divisions are thin labelled rules inside one continuous list. Enough separation, or too subtle?
  • Keypad coordinates stack on two lines and are omitted entirely for rows that cannot be entered. Correct emphasis against the LIDO reference values?
  • Below 760px the row reflows to two lines and DIS/RDIS move to the right edge. Check that the rail and the keypad values survive that layout.
